task-0274-js-left-shift-overflow · JS left shift overflow

Prompt 
```js
console.log(1 << 31);
```
What number does this print? (Note the sign bit.)
Model answer 
**It prints `-2147483648`.**

**Why:** JavaScript's bitwise operators (`<<` included) convert operands to **signed 32-bit integers** and return a signed 32-bit result. Shifting `1` left by 31 positions sets the most significant bit (bit 31), which is the sign bit:

```
10000000 00000000 00000000 00000000
```

Interpreted as a two's-complement signed 32-bit integer, that bit pattern is −2³¹, i.e. **−2147483648** — not the +2147483648 you'd get from treating it as an unsigned value.

If you want the unsigned interpretation, you'd use the unsigned right shift to coerce it, or do it mathematically:

```js
console.log((1 << 31) >>> 0);        // 2147483648
console.log(2 ** 31);                // 2147483648
console.log(1 << 30 * 2 /* etc */);  // n/a — bitwise ops cap at 32 bits
```

task-0246-cap-theorem-precise-statement · CAP Theorem Precise Statement

Prompt 
State the CAP theorem precisely. Name the three guarantees, and explain which guarantee a CP system sacrifices when a network partition occurs.
Model answer 
## CAP Theorem (Brewer's Theorem, proved by Gilbert & Lynch, 2002)

**Statement:** In a distributed data system, it is impossible to simultaneously guarantee all three of the following properties: **Consistency**, **Availability**, and **Partition tolerance**. In particular, when a network partition occurs, the system must sacrifice either consistency or availability.

## The Three Guarantees

1. **Consistency (C):** Every read receives the most recent write (or an error). Formally, this is *linearizability* — there exists a total order on operations such that every read returns the value of the most recent write preceding it in that order, as if all nodes accessed a single copy of the data.

2. **Availability (A):** Every request received by a non-failing node must eventually result in a (non-error) response. The system remains responsive, though the response is not guaranteed to reflect the latest write.

3. **Partition Tolerance (P):** The system continues to operate despite an arbitrary number of messages being dropped, delayed, or lost by the network — that is, despite the network splitting into mutually unreachable groups of nodes.

## What a CP System Sacrifices

A **CP system** keeps **Consistency** and **Partition tolerance**, so it sacrifices **Availability** during a partition.

Since the network cannot deliver messages between the partitioned groups, no node can know with certainty what writes occurred on the other side. To ensure every read returns the most recent write, a CP system must refuse to serve requests on nodes that cannot reach the majority/quorum of nodes (or on whichever partition cannot confirm it holds the authoritative state). Clients contacting the isolated partition receive errors or timeouts.

**Examples:** ZooKeeper, etcd, HBase, and MongoDB (with default write concerns) behave this way — they prefer to become partially unavailable rather than serve potentially stale data.

## Two Common Clarifications

- Partition tolerance is not really optional: since network failures are unavoidable in distributed systems, the theorem is best read as "**when** a partition happens, choose C or A." The trade-off only arises during partitions; in normal operation both C and A are achievable.
- This trade-off motivated extensions like **PACELC**: if Partitioned, trade Availability vs. Consistency; Else, trade Latency vs. Consistency.

# Resilient Autoscaling Design

**Core principles:** scale out fast and in slowly (hysteresis), react to *leading* indicators (queue depth) not just lagging ones (latency), keep health-check removal independent from scaling decisions, and never let automation be the only path to capacity change.

## 1. Collect the Right Metrics

No single metric captures saturation — collect a composite at 10–30s resolution via agent/telemetry pipeline (Prometheus, CloudWatch, etc.):

- **CPU utilization** — per instance and fleet-wide. Use p95 or trimmed mean across the fleet, *excluding instances failing health checks* (a dead instance reporting 0% CPU must not drag the average down and trigger scale-in).
- **Request latency** — p95 and p99, never averages (averages hide tail latency). This is a *lagging* signal: by the time it moves, users are hurting. It should trigger aggressive scale-out.
- **Queue depth** — per-instance request queue depth or wait time (and upstream message-queue lag if async workers are involved). This is the *leading* signal: it grows before latency degrades.
- **Secondary signals:** request rate/concurrency, 5xx error rate, memory (alert only — scaling on a leak scales forever), connection-pool saturation, and a "warm-up" flag from each instance so newly booted instances are excluded from scaling math until ready.

## 2. Define Autoscaling Thresholds

Calibrate via load testing, then use asymmetric thresholds (defaults shown):

| Condition | Direction | Threshold | Window |
|---|---|---|---|
| CPU | Out | > 65% | 1–2 min sustained |
| p99 latency | Out | > SLO (e.g., 300 ms) | 2 evaluation periods |
| Queue depth/instance | Out | > 100 (or wait > 50 ms) | 1 min |
| **All** of CPU < 30%, latency < 50% of SLO, queue ~0 | In | — | 10–15 min sustained |

- **Scale-out:** fast — step scaling (add 25–50% of current fleet, capped) with a short 30–60s cooldown so metrics reflect new capacity.
- **Scale-in:** conservative — 1–2 instances per action with a 5–15 min cooldown to prevent flapping.
- **Bounds:** `min` = capacity for baseline traffic + headroom (never 0 for an API); `max` = budget/quota cap. Set scale-out thresholds well below saturation, since metric lag + boot + warm-up typically costs 1–3 minutes of reaction time.

- **Liveness** (`/healthz`, shallow): process is alive. Interval 5–10s, timeout ~2s, 2–3 consecutive failures to mark unhealthy — avoids removing instances for transient blips.
- **Readiness** (`/readyz`, verifies warm-up and critical dependencies): gates *load balancer membership*. Fail readiness → instance is **removed from rotation but not terminated**, so it can recover.
- **Removal lifecycle:** mark unhealthy → deregister from LB → drain connections gracefully (finish in-flight requests, e.g., 30s draining window) → only then terminate/replace. SIGTERM handler must stop accepting new traffic first.
- **Guard against feedback loops:** replacement of failed instances must not count as scale-in or be blocked by scale-in cooldowns. If instances are being replaced faster than they can become healthy (crash-loop), halt scale-in and alert — that's a death-spiral signature, not a scaling problem.

- **Scale-in path:** sustained all-clear → deregister + drain → terminate. Prefer removing instances with least connections.
- **Guardrails:** scale-out wins on conflicting signals; max one scale-in per stabilization window; instance protection during deployments; pre-warmed capacity or scheduled scaling ahead of known traffic events.
- **Pressure valve:** load shedding (429s) when at max capacity, so the backend survives the gap while automation catches up or humans intervene.

- **Critical:** at `max` capacity and still saturated (automation exhausted); failed scale action (quota/launch errors); instance churn rate above threshold (crash-loop); SLO burn-rate alerting that runs *independently of autoscaling*, so a broken autoscaler still pages someone.

**Manual override:**

## Guiding Principles

- **Parallel Change (expand/contract):** old and new structures coexist; the "source of truth" moves explicitly: old → dual → new.

3. Build a **data-access abstraction layer** (repository/DAO) so old↔new mapping logic is isolated and flag-controlled.

3. Reconcile the delta until drift converges (this covers writes that occurred before dual-write deployed, if you backfill first).

- **Shadow/dark reads:** read from new in parallel, compare to old, log discrepancies, but still serve old.

- Flip the read flag: canary percentage → 100%. New schema serves reads; **dual-write continues**, so old remains fully current.

**Rollback:** flip the read flag back — instant, because old has never stopped being written.

## Phase 5 — Cutover Writes (New Becomes Source of Truth)

- Flip the write-authority flag: new is authoritative; **keep writing old** (now purely for rollback) in the same transaction.
- Keep this window short; the reconciliation job confirms old stays consistent.
- After a confidence period (days–weeks of clean metrics), stop writing old.

**Rollback:** flip the write flag back. Since dual-write to old never stopped, reverse-reconciliation of the window is typically zero-drift — verify, don't assume.

## Phase 6 — Contract (Destructive, Last)

- Take a **fresh snapshot**, then drop old columns/indexes/table.
- Enforce the deferred `NOT NULL`/unique constraints on the new schema.
- Remove flags, dual-write code, and the abstraction layer.

| Phase | Rollback action | Cost |
|---|---|---|
| 1–2 (expand, backfill) | Disable flags / kill backfill; drop new objects | Seconds |
| 3–4 (reads on new) | Flip read flag (old still fully current) | Seconds |
| 5 (writes on new) | Flip write flag + reverse-reconcile window | Minutes |
| 6 (old dropped) | Snapshot restore + WAL/binlog replay | Hours — avoid via long soak |

- **Missed writers** (batch jobs, stored procs) → drift; mitigate with the Phase 0 inventory or CDC-based sync that captures *all* writes at the log level.
- **Backfill clobbering fresh dual-written rows** → enforce watermark checks.
- **ID semantics:** preserve primary keys; never let the new table generate its own.
- **Constraint failures late:** deduplicate and validate *before* adding unique indexes.
- Semantic differences in defaults, timezones, or collation — caught by shadow reads in Phase 3, which is why that gate exists.
