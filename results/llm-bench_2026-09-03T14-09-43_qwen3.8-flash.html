  for (const op of operations) {
    if (op[0] === "get") {

      if (cache.has(key)) {

        cache.delete(key);

- If this alert fires, automation may attempt a restart.

- It must escalate to a human if verification fails.

### 2. Build the detection and remediation automation

Create an automation service or job that receives the alert and performs the runbook steps in a controlled way.

This replaces the engineer’s manual SSH session. Prefer a managed execution method such as:

- Kubernetes: `kubectl rollout restart deployment/...`
- systemd: `systemctl restart service`
- Cloud API: ECS task replacement, Cloud Run revision, VM service restart
- Ansible or SSH wrapper with audit logging, if SSH is unavoidable
- Internal service-management API

The automation should follow this flow:

```text
Receive alert
  -> validate alert
  -> acquire lock / prevent duplicate runs
  -> detect and confirm condition
  -> check safety constraints
  -> remediate
  -> verify
  -> update status page
  -> record audit log
  -> escalate if needed
```

Example pseudo-code:

```python

        return
```

- **Secure**: it uses service accounts, short-lived credentials, and least privilege.
- **Fail-safe**: if it cannot verify success, it escalates instead of continuing.

## Ordered zero-downtime migration plan

Use an **expand-and-contract / parallel-schema migration**. The rule is: never make a destructive change until the new structure is proven, and keep the old structure available as a rollback path until the new one is authoritative.

---

# 1. Prepare the migration

Before touching the live table:

1. **Inventory the current table**
   - Columns, indexes, constraints, triggers, foreign keys, views, stored procedures, jobs, ORM models, and application code paths that read/write it.
   - Identify hot rows, large indexes, and queries with high lock risk.

2. **Define the target schema**
   - New columns or new table structure.
   - Data types, nullability, defaults, indexes, and constraints.
   - Decide whether the migration is:
     - adding columns to the same table, or
     - creating a new parallel table and migrating rows into it.

3. **Make the change reversible**
   - Use feature flags for:
     - writing to new schema
     - reading from new schema
     - reconciling old vs new
   - Keep old schema live until the end.
   - Take a backup or snapshot, but do not rely on restore as the primary rollback mechanism.

4. **Add observability**
   - Metrics for:
     - query latency
     - write latency
     - error rates
     - replica lag
     - lock waits
     - backfill throughput
     - reconciliation mismatches
   - Logs/traces that show whether a read/write used old or new schema.

---

# 2. Create the new schema in parallel

Create the new columns or new table without affecting existing traffic.

## If adding columns to the same table

Use online DDL where supported, for example:

```sql
ALTER TABLE core_table
  ADD COLUMN new_col_1 type NULL,
  ADD COLUMN new_col_2 type NULL;
```

Guidelines:

- Make new columns nullable initially.
- Avoid expensive defaults that rewrite the table.
- Avoid adding `NOT NULL`, `UNIQUE`, foreign keys, or other constraints until data is backfilled and validated.
- Create indexes online:
  - PostgreSQL: `CREATE INDEX CONCURRENTLY`
  - MySQL: `ALGORITHM=INPLACE, LOCK=NONE` where supported
  - SQL Server: online index creation if available

## If restructuring into a new table

Create a new table, for example:

```sql
CREATE TABLE core_table_new (
  id type PRIMARY KEY,
  old_field type,
  new_field type,
  ...
);
```

Then create any needed indexes online.

If the application cannot immediately write to both tables, use one of:

- database triggers to mirror writes
- change-data-capture / logical replication
- application-level dual-write after code deployment

Triggers are simpler but can add write latency; application dual-write is more explicit and often safer for complex migrations.

---

# 3. Deploy application code that understands both schemas

Deploy code that is compatible with both the old and new structures, but keep the new behavior disabled.

The application should now be able to:

- read from old schema
- optionally read from new schema
- write to old schema
- optionally write to new schema
- compare old and new values in shadow mode

```text
write_to_new_schema = false
read_from_new_schema = false
shadow_read_compare = false
reconcile_old_new = false
```

Important:

- The deployed code must not assume the new schema is populated yet.
- Old clients must still work with the new columns/table present.
- New clients must still work if the new schema is empty or partially backfilled.

---

# 4. Backfill existing data into the new columns or table

Backfill historical data from the old structure into the new structure.

## Backfill strategy

Use an idempotent, throttled, resumable batch process.

Example pattern:

```sql
INSERT INTO core_table_new (id, new_col_1, new_col_2, ...)
SELECT id, old_col_1, old_col_2, ...
FROM core_table_old
WHERE id > :last_id
  AND id <= :last_id + :batch_size
ON CONFLICT (id) DO UPDATE
SET new_col_1 = EXCLUDED.new_col_1,
    new_col_2 = EXCLUDED.new_col_2;
```

For a large table:

- process in chunks, for example 1,000 to 100,000 rows depending on load
- checkpoint the last processed ID or timestamp
- retry failed batches idempotently
- throttle to avoid saturating the database
- run during low traffic if possible, but do not require downtime
- monitor replica lag and lock waits

## Backfill correctness

The backfill must handle rows changed while it runs.

Do not assume a single pass is enough. Use:

1. initial bulk backfill
2. delta backfill for rows modified during the bulk pass
3. final reconciliation

A common approach:

- Backfill rows with `updated_at <= start_time`.
- Then run a delta job for rows with `updated_at > start_time`.
- Repeat until the delta backlog is near zero.
- Enable dual-write before finalizing the delta.

---

# 5. Verify the backfill before enabling dual-write

Run automated validation.

## Checks

1. **Row count**

```sql
SELECT COUNT(*) FROM core_table_old;
SELECT COUNT(*) FROM core_table_new;
```

2. **Nullability / required field checks**

For example:

```sql
SELECT COUNT(*)
FROM core_table_new
WHERE new_col_1 IS NULL;
```

3. **Checksum comparison**

Compare aggregate values:

```sql
SELECT
  COUNT(*),
  SUM(id),
  MIN(created_at),
  MAX(created_at),
  SUM(LENGTH(new_col_1::text))
FROM core_table_new;
```

Run equivalent checks on old data.

4. **Sample row comparison**

Randomly sample rows and compare old and new values.

5. **Business invariant checks**

For example:

- total balances match
- order status counts match
- unique key counts match
- referential integrity holds
- no orphan rows if applicable

6. **Index and constraint validation**

- Confirm indexes are valid.
- Confirm no failed index builds.
- Confirm no lock storms or replication lag.

Do not enable dual-write until validation passes.

# 6. Enable dual-write

Now make new application writes go to both old and new structures.

Feature flag:

```text
write_to_new_schema = true
```

Write path:

```text
client request
  -> write old schema
  -> write new schema
  -> return success
```

Implementation choices:

## Option A: application-level dual-write

The application writes to both places in the same transaction if possible.

Example:

```sql
BEGIN;

UPDATE core_table_old
SET ...
WHERE id = :id;

INSERT INTO core_table_new (...)
VALUES (...)
ON CONFLICT (id) DO UPDATE
SET ...;

COMMIT;
```

This gives strong consistency if both tables are in the same database.

## Option B: database triggers

Use triggers on the old table to mirror inserts, updates, and deletes into the new table.

Pros:

- no application change needed for writes

Cons:

- harder to debug
- can increase write latency
- may miss application-level validation
- risky with complex transformations

## Option C: CDC / logical replication

Capture changes from the old table and apply them to the new table.

Pros:

- decouples application from migration
- good for large tables

Cons:

- eventual consistency unless carefully ordered
- requires reconciliation
- more operational complexity

For a core table with no data loss, prefer **transactional dual-write** if feasible.

# 7. Reconcile drift created before dual-write

Even after enabling dual-write, there may be a window where:

- old rows were not backfilled
- rows changed during backfill
- dual-write failed for some requests
- code paths missed one table

Run a reconciliation job.

The reconciler should:

1. Compare old and new rows by primary key.
2. Detect:
   - missing rows in new
   - extra rows in new
   - mismatched values
   - deleted rows
   - rows updated after backfill but before dual-write
3. Repair mismatches idempotently.
4. Record mismatch counts as metrics.
5. Alert if mismatches exceed a threshold.

Continue reconciliation until mismatch count is zero or within an agreed tolerance.

# 8. Enable shadow reads and compare results

Before cutting over reads, make the application read from the old schema but also read from the new schema asynchronously or in shadow mode.

Feature flag:

```text
shadow_read_compare = true
read_from_new_schema = false
```

Behavior:

```text
client request
  -> read old schema
  -> return old result to client
  -> asynchronously read new schema
  -> compare old vs new
  -> log mismatches
```

Do not expose new reads to clients yet.

## Compare

For each read:

- row exists in both?
- all projected columns equal?
- ordering equal?
- pagination equal?
- aggregate values equal?
- null handling equal?
- timezone/encoding/collation equal?

Log mismatches with enough context to debug:

- query name
- request ID
- primary key or filter
- old value
- new value
- timestamp

Run shadow reads for a meaningful period:

- enough to cover normal traffic
- peak traffic
- batch jobs
- admin operations
- rare edge cases

If mismatches occur, fix the new schema, backfill, dual-write, or query logic before proceeding.

# 9. Cut over reads to the new schema

Once dual-write and reconciliation are stable and shadow reads match, switch reads to the new schema.

Feature flag:

```text
read_from_new_schema = true
shadow_read_compare = true
```

Behavior:

```text
client request
  -> read new schema
  -> return new result to client
  -> optionally compare against old schema in shadow mode
```

Keep writing to both old and new during this phase.

This is the safest read cutover because:

- new data is already being written
- old data is still available
- if new reads are bad, you can flip back to old reads immediately
- no data has been lost

Monitor closely:

- read latency
- error rate
- timeouts
- mismatch alerts
- query plans
- index usage
- cache hit rates
- replica lag

If problems appear:

```text
read_from_new_schema = false
```

Then continue writing to both and investigate.

---

# 10. Cut over writes to the new schema

Only after reads have been stable for a sufficient period, make the new schema the primary source of truth.

Feature flag:

```text
write_to_new_schema = true
write_to_old_schema = true
```

At first, keep writing to both.

Then switch write priority:

```text
primary write target = new schema
secondary write target = old schema
```

The application should treat the new table as authoritative while still mirroring to old for rollback.

Example:

```text
client request
  -> write new schema
  -> write old schema
  -> return success
```

If both writes are in the same transaction, this is straightforward.

If they are separate, you need reconciliation to detect:

- new write succeeded but old write failed
- old write succeeded but new write failed

Prefer transactional writes when possible.

---

# 11. Stop writing to the old schema

After the new write path is proven, stop mirroring to the old schema.

Feature flag:

```text
write_to_old_schema = false
read_from_new_schema = true
```

Now the new schema is authoritative.

Keep the old schema present for a rollback retention period, but do not rely on it for reads or writes.

Before this step, ensure you have a rollback plan that can recover changes made to the new schema.

# 12. Contract the schema

Only after a retention period, remove the old structure.

Possible cleanup:

- drop old columns
- drop old table
- remove triggers
- remove dual-write code
- remove compatibility flags
- remove reconciliation jobs
- update ORM models and queries

Do this in a separate migration, not immediately after cutover.

Suggested retention:

- at least one full business cycle
- enough time to detect delayed bugs
- enough time to recover from operational incidents

Example:

- 7 days for low-risk changes
- 30 days for core transactional data
- longer if regulatory or financial correctness is involved

# Rollback plan

Rollback must be possible at every phase.

## Phase: new schema created

Rollback:

- drop new columns or new table
- no data loss because old schema untouched

Risk:

- low

---

## Phase: application code deployed

Rollback:

- disable feature flags
- deploy previous application version if needed

Risk:

- low, as long as code is backward compatible

---

## Phase: backfill running

Rollback:

- stop backfill job
- truncate or drop new table/columns
- leave old schema unchanged

Risk:

- low, provided no writes have been cut over

---

## Phase: dual-write enabled

Rollback:

```text
write_to_new_schema = false
```

Then:

- continue using old schema
- stop mirroring to new schema
- optionally truncate new schema
- fix issues and retry

Risk:

- low, as long as old schema is still authoritative

---

## Phase: shadow reads enabled

Rollback:

```text
shadow_read_compare = false
```

No client impact because reads still come from old schema.

Risk:

- very low

---

## Phase: reads cut over to new schema

Rollback:

```text
read_from_new_schema = false
```

Because writes are still going to both old and new, the old schema remains complete and can serve reads again.

Risk:

- low to moderate depending on how long new reads have been live

---

## Phase: writes cut over to new schema but old still mirrored

Rollback:

```text
primary write target = old schema
write_to_old_schema = true
write_to_new_schema = true
read_from_new_schema = false
```

If some changes were written only to new and not to old, run reverse reconciliation:

```text
new -> old
```

This is why you keep dual-write longer than necessary.

Risk:

- moderate

---

## Phase: old writes stopped

Once you stop writing to the old schema, rollback becomes harder.

Before doing this, ensure you have one of:

1. **Reverse dual-write**
   - Write to new as primary.
   - Mirror to old for a retention period.
   - If rollback is needed, switch back to old and reconcile any final drift.

2. **CDC from new back to old**
   - Keep a change feed from new table to old table.
   - On rollback, replay new changes into old.

3. **Backup/restore**
   - Use only as a last resort because it can cause data loss if not carefully timed.

Preferred rollback:

```text
read_from_new_schema = false
write_to_old_schema = true
write_to_new_schema = true
```

Then run reconciliation from new to old for any writes that happened while old was not being written.

Risk:

- high if old writes were stopped without a reverse sync path

---

## Phase: old schema dropped

Rollback:

- restore from backup
- recreate old schema
- reverse backfill from new to old

Risk:

- highest

Therefore, do not drop the old schema until you are confident and the retention period has passed.

---

# Recommended safe ordering summary

1. **Create new schema in parallel**
   - Add columns or create new table.
   - Use online DDL.
   - No constraints that require data rewrite.

2. **Deploy compatible application code**
   - Support old and new.
   - Feature flags disabled.

3. **Backfill old data into new schema**
   - Idempotent batches.
   - Checkpointed.
   - Throttled.
   - Re-run delta backfill.

4. **Validate backfill**
   - Counts, checksums, samples, business invariants.

5. **Enable dual-write**
   - Write to both old and new.
   - Prefer transactional writes.

6. **Reconcile drift**
   - Repair mismatches.
   - Monitor until zero drift.

7. **Enable shadow reads**
   - Serve from old.
   - Compare with new.
   - Fix mismatches.

8. **Cut over reads**
   - Serve from new.
   - Keep writing to both.
   - Keep shadow comparison if possible.

9. **Cut over writes**
   - Make new primary.
   - Keep mirroring to old.
   - Keep reconciliation available.

10. **Stop old writes**
   - Only after confidence and rollback path exists.

11. **Retain old schema**
   - Keep for rollback window.

12. **Drop old schema**
   - Final cleanup after retention.

---

# Key safety rules

- Never drop or rename old columns before the new schema is authoritative.
- Never add blocking constraints before backfill.
- Never rely on a single backfill pass.
- Never cut over reads until dual-write is stable.
- Never stop writing to the old schema until reverse rollback is possible.
- Never consider the migration complete until reconciliation has run over a full traffic cycle.

  const indegree = new Map();
  const dependents = new Map();

  for (const project of projects) {
    indegree.set(project, 0);
    dependents.set(project, []);
  }

  for (const [a, b] of deps) {
    if (!known.has(a) || !known.has(b)) continue;
    indegree.set(a, indegree.get(a) + 1);
    dependents.get(b).push(a);

    heap.push(value);
    let i = heap.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (heap[parent] <= heap[i]) break;
      [heap[parent], heap[i]] = [heap[i], heap[parent]];
      i = parent;

    const last = heap.pop();

      let i = 0;

          smallest = right;

        i = smallest;
      }
    }

    return top;

    if (indegree.get(project) === 0) {
      push(project);
    }
  }

    order.push(project);

      indegree.set(dependent, nextDegree);

      if (nextDegree === 0) {

      }

Model answer 
The **CAP theorem** states that a distributed data system cannot simultaneously guarantee all three of the following properties when a network partition occurs:

1. **Consistency** — every read returns the most recent write, or an error; often formalized as **linearizability**.
2. **Availability** — every request to a non-failed node receives a non-error response within some time bound.
3. **Partition tolerance** — the system continues to operate despite arbitrary message loss or delay between nodes.

More precisely: **any replicated distributed system must sacrifice either consistency or availability during a network partition.**

A **CP system** prioritizes **Consistency** and **Partition tolerance**, so when a network partition occurs it sacrifices **Availability**. It may reject requests, time out, or prevent the minority side of the partition from serving reads/writes in order to avoid inconsistent results.
