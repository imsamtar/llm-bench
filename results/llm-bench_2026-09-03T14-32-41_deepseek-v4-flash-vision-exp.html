To debug a slow memory leak in a long-running daemon, use an ordered, hypothesis-driven approach. The goal is to turn a vague symptom (“RSS grows until OOM”) into a concrete allocation stack trace, fix it, and prove the fix.

## 1. Reproduce the leak in a controlled way

Run the daemon in an isolated environment with a reproducible workload that mimics production traffic. The workload must be constant so any memory growth is due to the daemon, not input variation.

- Set up a test harness that drives the daemon with a fixed number of requests per second, for hours.

**Tools:** `top`, `ps`, `/proc/<pid>/status`, `smem`, `pidstat`, `perf mem`, or a custom script polling RSS/PSS.

## 2. Capture heap snapshots at two points in time

Take two heap profiles: one shortly after startup/warmup, and one later after the memory has grown significantly. The exact timing matters—the first snapshot should capture the steady-state baseline, the second should capture the leaked memory.

- If the daemon is written in a language with a VM (Java, Python, Go), use the language’s heap profiler.

**Tools:**

- **C/C++ etc.:** `valgrind --tool=massif`, `heaptrack`, `gperftools` heap profiler (`heap-profiler`), `jemalloc` with `mallctl` profiling, `tcmalloc` heap profiler. These generate heap snapshots with call stacks.

For C/C++ heap profilers, compare the “total heap” and “growth” between snapshots (Massif has `ms_print` and `ms_diff`; heaptrack has `heaptrack_print --diff`). For Java MAT, use “Histogram” with retained sizes and compare with “Compare to baseline”.

- Look for memory blocks whose count grows proportionally with time—those are leak candidates.
- Distinguish between:
  - **Real leaks:** memory no longer reachable and never freed.
  - **Logical leaks:** memory is still reachable but grows forever (e.g., unbounded caches, queues, session maps).
  - **Memory fragmentation:** total heap grows but live bytes stable.

**Tools:** `ms_print`, `heaptrack_print`, `jhat`, Eclipse MAT, `jmap -histo`, `pprof -top -diff_base`, `gperftools pprof`.

- The stack trace often shows a call that creates objects that are never freed or a data structure that keeps attaching entries.

- For logical leaks, inspect whether a cache/TTL is missing or whether a list grows faster than it is pruned.

**Tools:** `gdb` with breakpoints, `perf` with tracepoints, `bpftrace`/`eBPF`, `strace -f -e trace=brk,mmap`, static code review, or a custom logging counter.

**Tools:** Valgrind memcheck/ASan+LSan, `heaptrack` final analysis, `-fsanitize=address` in debug builds, CI soak tests, RSS monitoring.

- **Heap snapshot / profiler:** Valgrind Massif, heaptrack, gperftools, jemalloc/tcmalloc profilers; Java JFR/HPROF/Eclipse MAT; Go pprof; Python tracemalloc.
- **Comparison:** `ms_print`, `heaptrack_print --diff`, MAT “Compare Baseline”, `pprof -diff_base`.
- **Attribution:** gdb, bpftrace, perf, strace, source inspection.
- **Leak detection:** Valgrind Memcheck, AddressSanitizer/LeakSanitizer.
- **Fix validation:** soak tests, repeated heap diffs, RSS monitoring.

Model answer 
The CAP theorem states that a distributed data system can simultaneously guarantee only two of the following three properties:

1. **Consistency** — every read receives the most recent write or an error.
2. **Availability** — every request receives a non-error response, without the guarantee that it contains the most recent write.
3. **Partition tolerance** — the system continues to operate despite network partitions (message loss between nodes).

Because network partitions are unavoidable in distributed systems, partition tolerance is generally required. Therefore, during a partition, a system must choose between consistency and availability.

A **CP system** preserves **consistency** and **partition tolerance**, and sacrifices **availability**. Specifically, when a network partition occurs, a CP system may refuse to serve requests from nodes that cannot reach a quorum or ensure the latest data, returning errors or blocking rather than risking stale reads.
